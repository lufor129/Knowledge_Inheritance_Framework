# 跟 Git 主機結合：issue、PR、CI，同時支援 GitHub 和 GitLab

框架的工作流程建在 Git 主機都有的功能上，Agent 依設定檔用 gh 或 glab 操作：
- 變更提案就是 PR（GitHub）或 MR（GitLab）。
- 待回答和勘誤是 issue，用三類標籤分類：種類、知識庫，以及貼在提案上的來歷。
- CI 在每個提案上跑檢查程式；主線更新後，建置手冊網站和簡報，放在主機上供人下載。

主線只強制「檢查要過」，不強制「要有人核准」。原因是 GitHub 不允許作者核准自己的 PR，而我們決定維護者自己的提案由自己審。別人的提案要等維護者核准才合併，這一點靠約定和 Agent 把關。沒有 Git 主機時，退回手動模式。

## Consequences

- 平台不會擋「沒經過核准就合併」，我們也不另外限制誰能合併主線。「別人的提案要維護者核准後才合併」完全靠約定，加上 Agent 提醒：開 PR 時，Agent 會請維護者審；合併前，Agent 會提醒還沒有人核准。這是刻意的選擇，換來的是設定簡單，GitHub、GitLab 用哪種方案都一樣。
- 手動模式是第二套做法：待回答寫進常見問題、勘誤直接開變更提案。Agent 要能分辨目前是哪一種模式。
- 只用兩邊都有的功能，所以不用 GitHub 或 GitLab 獨有的功能，例如 GitHub Projects。
- Agent 會替不懂 Git 的同仁操作 Git，所以框架附一個 hook，擋掉強制推送、直接推主線、reset --hard、刪分支這類很難救回的指令；推分支照常可以。
- Agent 在 issue 和變更提案上的留言，開頭都標明「由 Agent 產生」，讓人分得出哪些是人寫的。
