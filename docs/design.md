## 目標與範圍

- 讓 Agent 協助各領域，把老手的經驗做成新人看得懂的簡報；新增、修改、查找、刪除都跟 Agent 說，Git 記下每一步。主角是新人。
- 只在公司內部使用，不對外發布。半導體是第一個知識庫；電腦視覺這類新領域照同樣方式加進來。

## 放在哪、聽誰的

- 框架和所有知識庫放在同一個 repo，全公司都能看；要限制閱讀範圍的知識不放進這套框架（ADR-0003）。
- 每個知識庫的內容就是一份簡報，新人從入口網站開始看（ADR-0006）。一頁放不下的長說明做成接在主頁後面的深入頁；沒有手冊，也就不用兩邊對照（ADR-0007）。

```
Knowledge_Inheritance_Framework/
├─ AGENTS.md          所有 Agent 共用的核心規則（CLAUDE.md 只有一行 @AGENTS.md）
├─ README.md          第一天指南、知識庫清單（程式產生）、框架維護者
├─ GLOSSARY.md        框架的用語表
├─ docs/adr/          決策紀錄
├─ .claude/skills/    kb-add、kb-change、kb-learn、kb-review、kb-new
├─ framework/         共用引擎（簡報、入口網站、互動圖樣板）、範本、工具；paths.md 是角色路徑
├─ CI 設定            檢查、建置、發布
└─ kb/<名稱>/
   ├─ README.md       介紹、維護者
   ├─ terms.md        術語表（主題索引從它產生）
   ├─ deck/           order.md（頁序）、<部分>/<章>.md（速覽、先修、主頁和深入頁的文字、自我檢查）、figures/（互動圖）
   ├─ widgets/        互動圖共用的程式
   ├─ assets/         圖片＋SOURCES.md（圖片清單）
   └─ dist/           建置結果，不進版控
```

## 角色

角色看當下在做什麼，不看資歷。

| 角色 | 做什麼 | 短指令 |
|---|---|---|
| 新人 | 從入口網站看簡報；請 Agent 查找、帶讀；沒寫或寫錯時跟 Agent 說 | /kb-learn |
| 傳承者 | 透過 Agent 新增、修改、刪除；認領待回答和勘誤。想開新知識庫的傳承者叫發起人 | /kb-add、/kb-change、/kb-new |
| 維護者 | 每個知識庫至少一位，名單寫在 README。審別人的提案；自己的提案自己審。不在時不特別處理，提案就等著 | /kb-review |
| 框架維護者 | 一開始是建立框架的人。核准規則、範本、引擎的修改和新知識庫；維護者離職時找人接手 | /kb-review |

短指令不用也可以，直接講中文，Agent 自己挑。

## 簡報

- 章檔（`deck/<部分>/<章>.md`）開頭寫速覽（必填）和先修（只標跨章、真的用得到的），接著是這一章的簡報頁，最後是「## 自我檢查」。寫法見 framework/guide/deck.md、writing.md。
- 主頁一頁講一個概念：標題、結論、重點、圖說、數字卡、比喻、旁白和出處；每頁都有圖，互動圖寫在 `deck/figures/`，先套樣板。
- 一頁放不下的長說明做成深入頁：「深入：主頁 id」接在主頁後面，「說明：」寫長文（多段、小標題、清單、表格、圖片、註腳），圖可以沿用主頁的。
- 頁 id 建立後不改名、不留別名；深入頁用主頁或主題的 id 加 `-d`。
- 數字用註腳附出處；這次新寫或改到的說法（深入頁的說明也算）沒附會擋，原本就有的列成可以慢慢補的工作。圖片要列進圖片清單，只寫出處，不寫授權。
- 自我檢查用 `<details>`，答案先收起來，每題寫「相關：」指向頁；深入題標【深入】。建置時每章最後自動產生一頁，所有題目也整理成問答附錄。
- 寫作方向是 ELI5：先白話、再術語，術語第一次出現附英文。由讀者測試把關，不列一長串原則。

## 新增、修改、刪除

- 新增有三種方式：研究（只給主題）、整理（給參考資料，原檔不放進知識庫）、訪談（口述；沒空當面講時，Agent 先把問題寫下來）。
- 三種都走同一條流程：簡報頁草稿（一頁放不下才建議做深入頁）→ 傳承者確認 → 檢查 → 讀者測試 → 變更提案（寫來歷）→ 維護者審核 → 正式內容。
- 修改主頁時，後面的深入頁和指向它的自我檢查一起確認；刪除或合併時，所有引用在同一個提案裡改完，不留舊 id。
- 一章一個變更提案；資料很多時可以整批整理，但還是一章一個提案。
- 審核只有核准和退回。退回就是要求修改，要附意見；沒有「不收」，真的不要的提案由傳承者自己撤回。維護者已經確定怎麼改的小地方（補出處、錯字、標籤）可以直接改在提案上，留言說明；內容要調整的一律退回。

## 把關

| 層 | 抓什麼 | 誰處理 |
|---|---|---|
| 程式擋 | id 重複、引用找不到、圖片不在清單；簡報頁沒有圖、章沒有速覽、先修指錯、深入頁接錯；術語表指到不存在的頁；這次新寫或改到的說法數字沒附出處 | 傳承者（Agent 代勞） |
| 程式提醒 | 原本就有、沒附出處的數字（用 `index.py --todo` 列出這些頁，慢慢補） | 維護者決定補出處或拿掉；傳承者開工時可以挑來補 |
| 讀者測試 | 寫得不清楚：沒背景的 Agent 只讀這章（每頁的文字、深入頁的說明和旁白），答不出自我檢查 | 傳承者改寫 |
| 維護者審核 | 內容說錯；圖好不好、會動會變的概念能不能操作 | 維護者 |

檢查在本機每改一次就跑（hook），開提案後 CI 再跑一次。元規則：先看到錯誤才加規則；能用程式擋的加進檢查程式，不能的才寫進 AGENTS.md。

## 新人怎麼學

- 從入口網站開始：一個資料夾，CI 打包成 portal.zip，解開後用 Chrome 或 Edge 打開，離線也能看。每個知識庫有全景圖（照部分和章自動排，先修畫成箭頭，點一章看速覽、時間和先修提醒，只提醒不擋）、學習路徑（時間和進度只算主頁，深入頁標「選看」）、主題索引（從術語表產生）；另外有角色路徑（framework/paths.md）、看到哪裡、跨知識庫搜尋。
- 主要看簡報：自學為主，有時有人帶。簡報照半導體範例：每頁一個概念，右邊依序是重點、數字卡、比喻卡，左邊放圖，會動、會變、有因果的概念要能操作；整份有章節頁、章節列、深入頁、自我檢查、出處頁、問答附錄。
- 每頁下面：旁白（預設收起）、看深入（後面有深入頁才有；深入頁平常翻頁不會經過，按這裡才進去，頁碼只算主頁）、問 Agent（複製這一頁的位置，貼到 Claude Code 接著問）；深入頁上還有說明（預設展開）、跳過深入、回主頁。看過的頁記在新人自己的瀏覽器裡，入口網站讀同一份紀錄。
- 查找只根據簡報回答（主頁、深入頁、自我檢查），附出處頁；兩頁說法不同時兩種都列，沒寫就說沒寫；先看程式產生的索引和術語表，不用向量檢索。
- 帶讀用白話解釋、反問、出小題目（選項長度差不多），最後指回那一頁。不在 repo 留新人的學習紀錄。

## 跟 Git 主機結合（ADR-0005）

| 框架 | GitHub／GitLab | 手動模式（沒有主機） |
|---|---|---|
| 變更提案 | PR／MR | 推上分支，產生訊息貼給維護者 |
| 待回答、勘誤 | issue，標籤：種類、kb:名稱 | 待回答寫進自我檢查標【待回答】；勘誤直接開提案 |
| 來歷 | 提案上的標籤：研究、整理、訪談 | 寫在訊息裡 |
| 檢查 | 本機 hook＋CI | 只有本機 hook |
| 入口網站、簡報 | 主線更新後 CI 建置，放在 Release；入口網站打包成 portal.zip | 請 Agent 現場建置 |
| Agent 用的指令 | gh／glab | git |

- 主線只強制 CI 檢查要過，不限制誰能合併。別人的提案要等維護者核准才合併，靠約定和 Agent 提醒。
- 新人說一句，Agent 先查重複，再問「要記下來嗎？」就開 issue，不用審核；提案寫 `Closes #N`，合併後 issue 自動關閉。
- 傳承者第一次用時，Agent 問他關心哪些知識庫，記在本機；開工時列出那些知識庫的 issue。
- 框架附一個 hook，擋強制推送、直接推主線、`reset --hard`、刪分支；推分支照常可以。
- Agent 在 issue 和提案上的留言，開頭標明「由 Agent 產生」。

## 情境（驗收用）

每個情境都要能只靠跟 Agent 說話完成，Git 操作全部由 Agent 代勞。

| 角色 | 情境 | 做完應該看到 |
|---|---|---|
| 新人 | 第一天 | 從 Release 下載入口網站（portal.zip），或 Agent 現場建置後打開；照學習路徑看簡報 |
| 新人 | 看不懂 | 根據簡報回答，附出處頁（主頁或深入頁）；可接著帶讀 |
| 新人 | 從簡報問 Agent | 貼上「我在看……這一頁」，Agent 讀那一頁和它後面的深入頁回答 |
