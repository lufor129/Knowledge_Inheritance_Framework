# 新增知識

主要目標是**新人好吸收**：資料正確只是起點，新人看一遍就懂才算做完。怎麼做見 framework/guide/deck.md 的「新人好吸收」。

## 開工：有什麼可以回答

使用者問「有什麼我可以做的」「有什麼我可以回答的」這類問題時：

1. `python3 framework/tools/who.py`：看使用者的名字和關心的知識庫。還沒記的就問，用 `who.py --set name=<名字> watch=<知識庫>,<知識庫>` 記下來，下次就不用再問。
2. 列出那些知識庫開啟中的待回答和勘誤：`gh issue list --state open --label kb:<知識庫> --json number,title,labels,assignees`。每題寫編號、題目、種類、有沒有人認領。
   再列出簡報裡數字還沒有出處的頁：`python3 framework/tools/index.py <知識庫> --todo`。這些沒有期限，挑一頁補出處就是一個變更提案（走 kb-change）。
   最後告訴使用者怎麼開始：說「我來回答 #N」認領一題，或說要補哪一頁的出處。
3. 使用者說「我來回答 #N」：`gh issue edit <N> --add-assignee @me`，再留言「🤖 由 Agent 產生」加「<名字> 認領」，讓別人知道這題有人在寫。然後從下面第 1 步開始，目標就是回答這一題。勘誤的修正走 kb-change。

## 新增

步驟多，開始前用 TodoWrite 列出下面十三步，做完一步勾一步。

問傳承者的時候都照 framework/guide/grill.md（追問）：一輪最多五題，每題附建議答案，查得到的自己查，問到每個分支都走過。寫之前先和傳承者有同樣的理解，比寫完再改省力。傳承者沒空，就停下來，等傳承者回到對話。

1. **開分支**：`git fetch origin && git switch -c kb/<知識庫>/<簡短英文> origin/main`。從最新的正式內容開，才不會和別人的改動打架。
2. **決定方式**，不確定就問：
   - **研究**：使用者只給主題。
   - **整理**：使用者給了資料（檔案、網址、舊簡報、照片）。
   - **訪談**：使用者要口述經驗，或答案只在使用者腦袋裡。
3. **對齊範圍**（研究才做）：照追問一輪一輪問：新人是誰、讀完要會什麼、哪些不放、要接上哪些已有的頁（已有的頁自己用 `index.py`、`read.py` 查）。最後列出新人需要知道的三到七個重點，傳承者說好再查。研究最花時間和費用，先對齊範圍才不會查了用不到的東西。
4. **蒐集**：
   - 研究：每個重點找一兩個第一手來源（官方文件、論文、原廠網頁）確認就夠；只找得到新聞或業界媒體的，註腳標「出處（報導）」（寫法見 writing.md）；什麼都找不到的數字不寫。
   - 整理：讀完資料，挑出新人需要的部分改寫成白話。原檔不放進知識庫，出處寫明它在哪裡。看不懂或互相矛盾的地方記下來，第 6 步拿出來問。
     材料裡有圖就主動挑：`python3 framework/tools/image.py extract <材料檔>` 取出圖片，一張一張看，挑出新人一看就懂的圖和流程圖，第 7 步列給傳承者選。公司內部資料不放。授權和放法見 writing.md 的「圖片」。
   - 訪談：照追問一輪一輪問，每題附上你的猜測，數字也猜一個。傳承者說的和出處、已有的頁不一樣時，當場追問；每一章問「新人最常誤會什麼」「什麼情況下這個說法不成立」。一直問到你能用自己的話講給新人聽、傳承者也同意為止。出處寫「名字（部門）口述，YYYY-MM」。

   完成：每個要寫進簡報頁的說法，都指得出來源（文件、網址或口述的人）。
5. **找位置**：`python3 framework/tools/index.py <知識庫>`。
   - 新內容放進最相關的章（章檔 `deck/<部分>/<章>.md`；先看 index.py 列的每章速覽），一章一個變更提案，維護者才審得動。
   - 用 `read.py <知識庫> --find <字>` 找已有的頁有沒有寫到同一件事、說法一不一樣。不一樣的，第 6 步拿出來討論（訪談時當場追問）。
   - 回答待回答時，答案寫進簡報頁（已有的或新的主頁、深入頁），再在那一章的「## 自我檢查」加一題，「相關：」連到那一頁。讀者測試的題目卷只有頁的文字、說明和旁白，答案只寫在題目裡就答不出來。
   - 跟已有的頁重複時，改成修改那一頁（kb-change）。
6. **討論查到的內容**（研究、整理才做；訪談本身就是這一步）：寫頁之前，把查到或讀到的全部攤開，照追問和傳承者討論：
   - 每個重點一段：說法、出處、第一手還是報導
   - 來源之間說法不同的地方、和已有的頁不一樣的地方、看不懂或互相矛盾的地方，各變成一題，附你的建議

   這些要附出處、說明比較長，用編號文字問。和已有的頁說法不同時，照 grill.md 的「追問」處理：由傳承者決定。傳承者說好才往下。
7. **分頁和圖的做法**：開始做頁之前，給傳承者一張表，一頁一行：

   | 頁 | 講什麼 | 圖怎麼做 | 另一種做法 | 範例頁 |
   |---|---|---|---|---|

   - 流程、會動、會變、有因果的概念，預設做成可以操作的互動圖，深入頁也一樣。從三種樣板挑，各附一頁半導體簡報當範例：拉桿看變化（`hk1`）、一步步播放（`gaaflow`）、點零件看說明（`depo4`）。傳承者想看範例時打開：`python3 framework/tools/get.py semiconductor deck --open --page <頁id>`。
   - 材料裡有好懂的圖或流程圖時，先放那張，不要重畫；上面是英文也沒關係，圖說寫中文就好。表上寫推薦哪張、好懂在哪裡，要不要另外做成互動圖，讓傳承者選。
   - 一頁放不下的細節（較長的推導、表格、很多出處，或口述的細節比一頁多很多），建議做成接在後面的深入頁，也寫在表上，由傳承者決定。

   傳承者看完改想改的，說好才開始做頁。
8. **做簡報頁**：照 framework/guide/deck.md 和第 7 步定好的表。新人主要看簡報，所以先想新人在這一頁看到什麼：
   - 一頁一個概念：結論、三到四點重點、數字卡、比喻、旁白；數字附出處註腳（寫法見 writing.md）。新的頁取新的頁 id，加進頁序 `deck/order.md`。
   - 互動圖先套樣板（`framework/engine/figures/templates.js`），套不上才自己寫；畫布上的東西先用共用畫法，顏色參考色票（都在 deck.md）。材料裡的圖用 `image.py add` 放進知識庫。框架以外的畫圖工具只在傳承者要求時用（寫法見 deck.md）。
   - 深入頁寫「- 深入：<主頁 id>」，長文寫在「說明：」，頁序裡緊接在主頁後面。
   - 新的一章：章檔開頭寫速覽（兩三句：學完會知道什麼、為什麼排在這裡）和圖示（從 deck.md 的圖示表挑一個）；真的要先看過別的章才看得懂，再寫先修。
   - 有新術語就在 terms.md 加一列；建議在那一章的「## 自我檢查」替新的頁加一題。
9. **事實查核**（研究、整理才做；訪談來的說法不查）：交給傳承者之前，另外請一個 Agent（子 Agent）查核，不要自己查自己。給它改過的頁 id、章檔路徑、每個說法的出處清單；不要給它你寫作的過程和理由，它才不會跟著錯。請它：
   - 抓每個出處的全文，逐句核對結論、重點、圖說、數字卡、深入頁說明和旁白：出處裡找得到嗎、指對段落了嗎、數字和因果對嗎
   - 看新人好吸收：頁和頁之間有沒有矛盾，有沒有說「前面講過」卻指到沒寫的內容
   - 提醒可能不該公開的內容（公司參數、客戶、事故細節）；只提醒，由維護者判斷
   - 每一條回報哪一頁、哪一句、什麼問題、依據是出處的哪一段

   照結果改，或把說法拿掉；改過的地方再請它查一次，最多兩輪。記下查了幾個來源、抓到並改了什麼、還留著的提醒，第 13 步寫進提案說明的「事實查核」。
10. **傳承者確認**：先自己照 deck.md 的「新人好吸收」看一遍，沒做到就先改，不要把表格初稿交出去等傳承者提醒。再用白話講改了什麼。交稿的訊息一定要有一段「為了新人好吸收，我這樣做」，列出這次的設計（例如流程做成一步步播放的圖、這個詞先白話解釋、哪張材料圖為什麼選它）。打開做好的頁給傳承者看：`python3 framework/tools/get.py <知識庫> deck --here --open --page <頁id>`。標出你不確定的地方，照傳承者的意見改。內容是傳承者的經驗，所以傳承者明確說好才往下走。
11. **檢查**：`python3 framework/tools/check.py <知識庫>`，到沒有 ✗ 為止。
    - 這次新寫或改到的說法（結論、重點、圖說、數字卡、深入頁說明的每一段），數字沒附出處會擋：補出處，或改成不帶數字的說法。
    - 新寫的旁白、自我檢查答案有數字沒出處、出處看不出是真的來源、互動圖裡寫了數字，檢查會用 △ 提醒。一樣補上；留著的話，簡報上會標「待查證」，開提案時告訴傳承者。
12. **讀者測試**：照 framework/guide/reader-test.md（讀者讀整章，只考和改過的頁有關的題目），全部答對才往下走。
    第 10 步之後又補了說法（例如為了讓讀者測試答得出來，多寫一段），開提案前把補的部分再給傳承者看一次，傳承者說好才算數。
13. **開變更提案**：commit 之後跑 `python3 framework/tools/proposal.py <知識庫> --source <研究|整理|訪談> --reader <n/n>`；回答 issue 時加 `--closes <N>`，合併後那個 issue 才會自動關閉。它會寫好說明的草稿 `.kif/tmp/proposal.md`：把「（……）」換成你的話（研究、整理時，「事實查核」那一段照第 9 步的紀錄寫），標題換成一句話，然後照它印出的指令推分支、開提案，再做「開好之後」那一步。
    追問時傳承者說過某一頁已有的說法錯了：提案開好之後，問要不要接著用 kb-change 改那一頁（另一個提案）。

完成：頁面新人看一遍就懂，傳承者說好了；提案開好了，使用者知道提案編號、在等誰審，以及合併後哪個 issue 會自動關閉。使用者要在這次對話裡合併時，先留審核紀錄（framework/guide/host.md）。
